01 · The model

Not a central lender gateway.
A federated distribution network.

The exchange separates route ownership from demand origination. A participant can originate business, supply lender routes, or do both.

01

Local route first

If the selected programme belongs to the participant, its Edge Gateway calls the lender directly from the participant environment.

02

Exchange when remote

If another member owns the route, the Edge Gateway sends a canonical transaction to the Finequs Exchange Hub.

03

Credentials stay local

The route-owning participant retains its lender keys, whitelisted endpoint, transformations and operational responsibility.

04

Status follows the same path

Provider callbacks are persisted and normalised at each hop, then returned to the originating participant using the pinned route.

04 · Route resolution

The router resolves a programme version—not a lender name.

One lender can expose several programmes through different owners. The selected programme pins one immutable route for the life of the submission.

05 · Exchange protocol

One canonical envelope across every hop.

The protocol records the origin, route owner and ultimate provider separately. Personal data should be referenced or encrypted wherever the intermediary does not need to inspect it.

08 · Trust model

Every node is trusted narrowly.

Network membership does not grant universal data access. Trust is established per participant, route, purpose, contract version and environment.

01

Node identity

Each Edge has a unique certificate, participant ID, environment and approved endpoint.

02

Route entitlement

Consumers can use only route versions explicitly shared with them.

03

Consent chain

Customer disclosure identifies the originator, intermediaries and ultimate regulated provider.

04

Credential custody

Provider keys remain in the vault controlled by the route-owning participant.

05

Immutable evidence

Configuration, submission, callback, failure and replay actions leave reconstructable audit records.

06

Commercial truth

Route ownership, schedule version and transaction outcome feed one exchange ledger.

09 · Team implementation sequence

Build the protocol once. Prove it through three routes.

  1. 01
    Freeze contracts

    Envelope, identities, programme/route versions, statuses, errors, signatures and compatibility policy.

  2. 02
    Establish trust

    Participant registration, node certificates, mTLS, signed requests, replay protection and environment separation.

  3. 03
    Prove local routing

    nStore Edge resolves and submits InCred without sending customer data through Finequs.

  4. 04
    Prove Finequs routing

    nStore Edge sends CASHe through the Exchange Hub and receives asynchronous statuses.

  5. 05
    Prove federation

    nStore sends Axis through Finequs to Fynaptic; callback returns across the pinned reverse path.

  6. 06
    Harden operations

    Retries, idempotency, dead letters, monitoring, reconciliation, security and load tests.

  7. 07
    Controlled activation

    Enable one route at a time after participant, provider, contractual and operational gates pass.
